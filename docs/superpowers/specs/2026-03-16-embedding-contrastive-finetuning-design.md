# EmbeddingGemma Contrastive Fine-Tuning Design

**Date:** 2026-03-16
**Replaces:** `2026-03-16-embeddinggemma-distillation-design.md`

## Problem

The base `google/embeddinggemma-300m` model fails on semantic/cultural queries where the query uses conceptual language that doesn't appear in item text. Examples:
- "Almoço estilo havaiano" (Hawaiian-style lunch) → should retrieve poke bowls
- "Monte seu próprio refogado" (Build your own stir-fry) → should retrieve raw ingredients
- "Sanduíche de bagel estilo Nova York" → should retrieve bagel-style items

These queries account for the worst nDCG scores in the semantic category (currently 0.540 overall).

## Approach

Contrastive fine-tuning with synthetic (query, item) pairs generated by GPT-4o-mini. The LLM generates diverse queries for each item, biased toward semantic-gap/cultural queries that require conceptual reasoning. Training uses MultipleNegativesRankingLoss, which treats other items in the batch as negatives — no manual negative mining needed.

## Data Generation

### Script
`scripts/generate_training_data.py`

### Process
1. Load all 5,000 items via `load_items()`
2. For each item, call GPT-4o-mini with item metadata (name, category, description, taxonomy)
3. Request 2 queries per item:
   - **Semantic-gap query:** Conceptual, cultural, or occasion-based. The query should NOT reuse the item's name or category directly. If the item is too generic for a meaningful semantic-gap query, return `null`.
   - **Direct query:** Uses different vocabulary than the item name but is still a reasonable search.
4. Few-shot the prompt with 4-5 examples from the real 60 queries to match query style.
5. Use concurrent API calls (max 20 concurrent) with exponential backoff on rate-limit errors (max 3 retries).
6. Save progress every 100 items to allow resuming from partial failures.
7. Output: `data/training_pairs.jsonl`

### Item Text Contract
**Critical:** The `item_text` field in training pairs must be the exact output of `build_item_text()` from `src/data_loader.py` — i.e., `item["text"]` as loaded by `load_items()`. The generation script must import and reuse `load_items()`, not reconstruct item text. This ensures the text the model learns to map queries to is identical to the text it will embed at inference time.

### LLM Prompt Template
```
System: You are a Brazilian food delivery search query generator. Given a food item from iFood,
generate search queries in Portuguese that a customer might type to find this item.

For each item, generate TWO queries:
1. "semantic_gap": A conceptual, cultural, or occasion-based query that does NOT reuse the
   item's name, category, or main keywords. Think about WHEN/WHY someone would order this,
   what cuisine or cultural context it belongs to, or what occasion it suits.
   Return null if the item is too generic (e.g., plain salt, cooking oil).
2. "direct": A straightforward query using different vocabulary than the item name.

Respond with JSON: {"semantic_gap": "..." or null, "direct": "..."}

Examples:
- Item: "Poke Tropical | Culinária Japonesa | Delicioso Poke Tropical... | ALIMENTOS_PREPARADOS/PRATOS/POKES_BOWLS"
  → {"semantic_gap": "almoço estilo havaiano", "direct": "tigela de peixe cru com arroz"}
- Item: "Feijoada Magra | Especial do Dia | ... feijão preto e carnes selecionadas | ALIMENTOS_PREPARADOS/PRATOS/FEIJOADAS"
  → {"semantic_gap": "prato típico brasileiro de sábado", "direct": "feijão preto com carnes"}
- Item: "Pimentão Verde Extra | Feira | Compra por peso | FLV/LEGUMES/PIMENTAO"
  → {"semantic_gap": "ingrediente para refogado caseiro", "direct": "legume verde para cozinhar"}
- Item: "Hot tofu | Hot roll | Enrolado empanado e frito com tofu... | ALIMENTOS_PREPARADOS/PRATOS/SUSHIS_SASHIMIS_TEMAKIS"
  → {"semantic_gap": "sushi vegetariano frito", "direct": "hot roll de tofu"}

User: {item_text}
```

### Output Format
```jsonl
{"query": "almoço estilo havaiano", "item_text": "Poke Tropical | Culinária Japonesa | ...", "query_type": "semantic_gap"}
{"query": "tigela de peixe cru com arroz", "item_text": "Poke Tropical | Culinária Japonesa | ...", "query_type": "direct"}
```

### Expected Scale
~8,000–10,000 pairs (some items will produce only 1 query when semantic-gap is `null`).

### API Configuration
- Model: `gpt-4o-mini`
- Endpoint: OpenAI API directly (not proxy)
- API key: `OPENAI_API_KEY` environment variable
- Temperature: 0.8 (encourage diversity)
- Structured JSON output via `response_format={"type": "json_object"}`

## Training

### Script
`scripts/train_embedding.py`

### Base Model
`google/embeddinggemma-300m` (768-dimensional, multilingual)

### Prompt Templates
**Critical:** EmbeddingGemma uses asymmetric prompt templates:
- Query prompt: `"task: search result | query: "`
- Document prompt: `"title: none | text: "`

These are baked into the model's `prompts` config and applied automatically by `SentenceTransformer.encode(prompt_name=...)`. During training, the `SentenceTransformerTrainer` must apply the correct prompts. Use the sentence-transformers dataset format with two columns named after the prompt keys:
- Column `"query"` → applies the query prompt template
- Column `"document"` → applies the document prompt template

This ensures the model learns in the same input format it uses at inference.

### Loss Function
`MultipleNegativesRankingLoss` (sentence-transformers built-in):
- Each batch of N (query, item_text) pairs creates N positives and N*(N-1) negatives
- For each query, its paired item is the positive; all other items in the batch are negatives
- Pushes query embeddings closer to their positive item, farther from in-batch negatives
- Larger batch size = more negatives = stronger signal

### Train/Validation Split
90/10 split of training pairs, stratified by `query_type`. Monitor validation loss during training to detect overfitting. If val loss increases for 2 consecutive evaluations, stop early.

### Hyperparameters
| Parameter | Value | Rationale |
|-----------|-------|-----------|
| Batch size | 64 | Maximizes in-batch negatives for MNRL |
| Epochs | 3 | Small dataset, avoid overfitting |
| Learning rate | 2e-5 | Standard for fine-tuning transformers |
| Warmup ratio | 0.1 | 10% of training steps |
| Weight decay | 0.01 | Light regularization |
| Eval steps | every 0.25 epoch | Monitor val loss for early stopping |
| Device | MPS | Apple Silicon GPU |

### Output
Model saved to `models/embeddinggemma-finetuned/` in sentence-transformers format.

## Evaluation

No pipeline changes needed. The existing `DenseRetriever` auto-detects local models.

### Process
1. Update `src/config.py`: `EMBEDDING_MODEL = "models/embeddinggemma-finetuned"`
2. Delete `eval_data/embedding_cache.pkl` (old entries from other models waste space; cache self-partitions by model name so leaving it is also safe, but a clean cache avoids confusion)
3. Run `uv run python run_eval.py --evaluate routed`
4. Compare against baseline on the 60 real GT queries (never used in training)

### Success Criteria
- Primary: nDCG@10 on semantic category improves over 0.540 baseline
- Secondary: Overall nDCG@10 improves over 0.669 baseline
- Guard rail: Keyword and negative category nDCG must not regress more than 5%

### Constraints
- All scripts assume working directory is the project root. The fine-tuned model path `models/embeddinggemma-finetuned` is relative — always run from project root.
